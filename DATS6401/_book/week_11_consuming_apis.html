Week 11 — Consuming APIs & Data Endpoints

The client side of client–server. This module teaches how a Streamlit app talks to a server over HTTP — REST basics, requests, JSON — through worked examples that consume ready-made endpoints, setting up the model-serving work to come.

📖 Background & Motivation

Until now, every app has been self-contained: the data and any computation live inside the Streamlit script. Real data-science applications rarely work that way. Data lives behind APIs, and models run on servers — separate processes, often on separate machines — that the front-end talks to over HTTP. Separating the client (the app the user sees) from the server (where data and models live) is what lets a visualization scale, stay secure, and reuse a model across many front-ends.

This week is deliberately client-only: we learn the request/response pattern by consuming endpoints that already exist, so the networking concepts land before we add the complexity of writing a server. You will hit public REST APIs and a small provided course endpoint, parse JSON responses into pandas, handle errors and latency gracefully, and visualize what comes back inside Streamlit. Next week (12) you build the server side; the week after (13) you visualize live model output. Think of these three weeks as one arc: consume → serve → visualize.

🔎 Learning Objectives

  • Explain the client–server model and the structure of an HTTP request/response.
  • Call REST APIs from Python with requests and parse JSON into pandas.
  • Handle errors, status codes, and latency gracefully in a Streamlit client.
  • Visualize data fetched live from an endpoint, with caching.

🧭 Two-Hour Session Outline

Single 2-hour block. The two worked examples you asked for live in Block 2.

Block 1 — Concepts & Theory (~25 min, PowerPoint)

  1. Client vs. server: why we separate them (8 min)
  2. Anatomy of an HTTP request: method, URL, params, headers, status codes (10 min)
  3. JSON as the lingua franca; latency and failure as design realities (7 min)

Block 2 — Guided Demonstration (~35 min, live coding) — Worked Examples

  1. Example A: call a public no-key API (Open-Meteo), parse JSON → pandas, chart it (15 min)
  2. Example B: call the course-provided endpoint, handle a non-200 status, cache the call (12 min)
  3. Wrap both into a Streamlit app with a fetch button and error handling (8 min)

☕ Break (~10 min)

Block 3 — Hands-On Activity (~40 min, students working)

  1. Students pick a public API and successfully fetch + parse it (15 min)
  2. Visualize the response in Streamlit with caching (15 min)
  3. Add graceful error handling for a bad request (10 min)

Block 4 — Wrap-Up & Homework Preview (~10 min)

  1. Share apps; discuss latency/error handling (6 min)
  2. Preview homework and Week 12 (you’ll build the server next) (4 min)

💻 Notebook / App Snippets

Example A — public API → pandas → chart

import requests, pandas as pd

r = requests.get(
    "https://api.open-meteo.com/v1/forecast",
    params={"latitude": 38.9, "longitude": -77.0, "hourly": "temperature_2m"},
    timeout=10,
)
r.raise_for_status()
data = r.json()["hourly"]
df = pd.DataFrame({"time": pd.to_datetime(data["time"]), "temp": data["temperature_2m"]})

Example B — robust call with caching

import streamlit as st, requests

@st.cache_data(ttl=300)
def fetch(url, params=None):
    r = requests.get(url, params=params, timeout=10)
    r.raise_for_status()        # raises on 4xx/5xx
    return r.json()

try:
    payload = fetch("https://api.restcountries.com/v3.1/all")
except requests.HTTPError as e:
    st.error(f"Request failed: {e}")
    payload = None

Client app skeleton

# app.py
import streamlit as st, requests, pandas as pd

st.title("API Client")
lat = st.number_input("Latitude", value=38.9)
lon = st.number_input("Longitude", value=-77.0)

if st.button("Fetch"):
    try:
        r = requests.get("https://api.open-meteo.com/v1/forecast",
                         params={"latitude": lat, "longitude": lon, "hourly": "temperature_2m"},
                         timeout=10)
        r.raise_for_status()
        h = r.json()["hourly"]
        df = pd.DataFrame({"time": pd.to_datetime(h["time"]), "temp": h["temperature_2m"]})
        st.line_chart(df.set_index("time"))
    except Exception as e:
        st.error(f"Could not fetch data: {e}")

🧪 In-Class Activity

  • Consume a public API and visualize the result in a Streamlit app with a fetch button.
  • Discuss:

What status code did you get, and what should the app do on failure?

What should be cached, and for how long (ttl)?

How does the app behave while waiting on a slow response?

Hints

# Always set timeout=, call raise_for_status(), and wrap fetches in try/except

🏠 Homework

  1. Choose a public REST API (or the course endpoint).
  2. Build a Streamlit client that fetches live data, parses it, and visualizes it.
  3. Include caching and graceful error handling for a failed request.
  4. Submit the runnable app (and the endpoint/params you used) to Blackboard.

Rubric (10 pts)

  • Correct request + JSON parsing into a usable structure (3)
  • Caching applied sensibly (2)
  • Graceful error/latency handling (2)
  • Clear visualization of the fetched data (3)

🧩 Optional Extensions

  • Add query widgets that change the request parameters live.
  • Page through a paginated API.
  • Compare two endpoints’ responses side by side.

✅ Submission Checklist

Before submitting, make sure:

  • Your assignment fulfills all the basic requirements listed above.

  • Your app runs locally with no errors and handles a failed request without crashing.

  • API calls are cached and timeouts are set.
